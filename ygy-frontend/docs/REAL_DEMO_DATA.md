# 실제 통합 시연 데이터 세트

DB 초기화로 주문과 패키지 ID가 매번 바뀌므로, 이 문서는 고정 연결 데이터를 기록하지 않는다. 고객 화면은 매장 번호만으로 해당 매장의 취소되지 않은 주문 한 건을 임의로 선택해 조회한다.

## 패널 구성

| 역할 | ID | 연결 패키지 | 확인 경로 |
| --- | --- | --- | --- |
| 고객 | 매장 `889`, `894`, `884` | 매장 주문 1건 | 매장 번호로 조회 |
| 사장님 | 매장 `889` | 강남 주문 | `NEW` 주문의 조리 시작 |
| 사장님 | 매장 `894` | 강남 주문 | `NEW` 주문의 조리 시작 |
| 사장님 | 매장 `884` | 홍대 주문 | `NEW` 주문의 조리 시작 |
| 라이더 | `rider_12` 등 | 강남 제안 | offers 조회·수락 |
| 라이더 | `rider_2` 등 | 홍대 제안 | offers 조회·수락 |

조리 시작 뒤 주문은 `COOKING`이 되며, 30초 클러스터링 주기 뒤 패키지가 `OFFERED`로 생성된다. 라이더 수락 뒤 패키지는 `MATCHING`, 주문은 `MATCHED`가 된다.

```text
GET /api/merchant/{store_id}
GET /api/customer/{선택된 주문 ID}
GET /api/merchant/889
GET /api/merchant/894
GET /api/merchant/884
GET /api/rider/rider_12/offers
GET /api/rider/rider_2/offers
```

## 읽기 전용 시연 원칙

- 초기화 이후 실제 상태 변경은 전용 테스트 환경에서만 수행한다.
- 화면은 5초마다 조회하지만, 제안 패키지 생성은 30초 클러스터링 주기를 기다려야 한다.
- 동일 주문 조합의 제안이 여러 개 보일 수 있으며, 라이더가 하나를 수락하면 된다.
